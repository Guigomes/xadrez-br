# CLAUDE.md — chess-viewer

Guia para sessões futuras do Claude Code neste repositório. Contexto completo da feature "torneios nativos" está em `docs/`.

## O que é este projeto

Plataforma de gestão de torneios de xadrez suíços (Next.js 15 + Supabase + Vercel). Dois modos de torneio coexistem:

- **`mode='native'`** (padrão, implícito para o organizador): o próprio sistema pareia rodadas com motor FIDE Dutch (bbpPairings compilado para WASM), gerencia inscrições, resultados, staff.
- **`mode='imported'`**: espelha um torneio já rodado no chess-results.com via worker `cron-import` (repo irmão, `Guigomes/xadrez-br-cron`). **Exclusivo do painel `/admin/dev`** — usuário comum nunca escolhe isso; só quem tem `role='admin'`.

- **`mode='app'`** (2026-10-21): torneio organizado no app Android Gambito Lite (`../gambito-lite`). O celular pareia e lança; o site só mostra (mesma visão somente leitura dos importados — em código, tratar com `mode !== 'native'`, não `=== 'imported'`). Backup privado em `lite_tournaments` (só o dono lê); publicar materializa nas tabelas do site via `lite_publish` reaproveitando os UUIDs do app; rotas `app/api/lite/*` autenticadas pelo token Bearer do app. Login do app volta por `/auth/callback?lite=1`, que só repassa o `code` ao app (PKCE feito no celular).

Repo separado: `cron-import` (Cloud Run Job, worker de importação) — vive em `../cron-import` neste workspace, próprio git.

**O importador existe só no `cron-import`.** Não recriar cópia dele aqui: a que existia em `lib/import/` ficou para trás (cortava a planilha em 150 linhas, sem casamento por CBX, sem PGN) e foi removida em 2026-10-22 — sobrou só `lib/import/notify.ts`, usado pelo sync do Lite. O botão "Dev: forçar sincronização" (`/api/admin/dev/force-import`) apenas marca `tournament_imports.force_requested_at`; o robô processa essas linhas primeiro na próxima execução (a cada 5 min, 9h–22h de Campo Grande), mesmo desligadas ou de torneio encerrado, e limpa a marca.

## Arquitetura essencial

- **RPC Postgres como única porta de mutação de estado estrutural.** Nunca fazer `UPDATE` direto do cliente em `rounds.status`, `tournaments.status` (fora do stepper já existente), `tournament_players`, etc. Toda transição de rodada/inscrição passa por RPC `security definer` (ver `supabase/migrations/020_lifecycle_rpcs.sql`, `025`, `026`).
- **Classificação: `standings` é a fonte; `tournament_players` guarda só cópia.** `standings` (nota, posição, desempates, jogos) é escrita por `recalculate_standings` (nativo) e pelo robô (importado). `tournament_players.current_score/current_rank/buchholz/buchholz_cut1/sonneborn_berger` são cópias denormalizadas, lidas por certificado, imagem de compartilhar, Minha área, perfil, chat e `get_round_pairings`. **Nunca escreva esses campos de `tournament_players` direto**: escreva em `standings` e chame `sync_player_scores_from_standings(torneio)` (service_role), que copia tudo num UPDATE só — é o que `recalculate_standings` e o robô fazem (migration `20261024120000`). `recalculate_standings` desempata posição igual por ranking inicial e id, de forma determinística (antes a posição de empatados trocava a cada recálculo). As colunas `direct_encounter` e `performance_rating` de `tournament_players` nunca foram escritas nem lidas (sempre nulas).
- **TRF(bx) é o formato pivô**: mesmo serializador (`lib/pairing/trf/serialize.ts`) alimenta a engine de pareamento E a exportação de homologação FIDE/CBX. Dois modos: `serializeForPairing` (entrada da engine) e `serializeForExport` (homologação, todas as rodadas).
- **Engine bbpPairings roda em WASM** dentro de API route Node (`lib/pairing/engine.ts`), instância nova por chamada, sem estado compartilhado. Artefatos commitados em `lib/pairing/wasm/` (não regenerar sem necessidade — ver `scripts/build-bbppairings.sh`).
- **RLS em toda tabela sensível.** Helpers centrais: `auth_user_role()`, `is_tournament_manager()`, `is_tournament_organizer()`, `is_organizer_or_admin()`, `is_arbiter_or_admin()` (migration 002, 018, 026).

## Achados críticos do spike WASM (não redescobrir)

- `-fexceptions` é **obrigatório** no build Emscripten — sem ele, erro de validação do TRF vira `abort()` mudo em vez de exit code 3 legível.
- Exit codes do bbpPairings: `0` sucesso, `1` **sem pareamento válido** (caso de negócio, não bug — grupo pequeno já se enfrentou tudo), `2` erro inesperado, `3` entrada inválida, `4` limite de tamanho, `5` erro de arquivo.
- `XXC white1|black1` é **obrigatório** (bbpPairings não sorteia cor, ao contrário do JaVaFo).
- bbpPairings **não é endossado pela FIDE isoladamente** — é o motor Dutch por trás do SwissSys (que É endossado). Nosso sistema completo nunca passou por endosso formal da FIDE. TRF exportado deve ser tratado como rascunho para revisão de árbitro humano, não homologação automática.

## Modelo de permissão (mudou nesta sessão — não confundir as duas camadas)

1. **`user_profiles`** (conta, global): `role` é só `admin` vs resto (não mais categoria única). `is_organizer`, `is_arbiter`, `is_participant` são **flags independentes que coexistem** — uma pessoa pode ser as três. Inscrição em torneio (`tournament_registrations`) continua aberta a qualquer um mesmo sem `is_participant` marcado; a flag existe pra habilitar **autopreenchimento** do formulário de inscrição a partir do perfil (migrations 027/028) e alimentar de volta o perfil após inscrever (best-effort, não bloqueia a inscrição se falhar). "Novo torneio" só aparece pra quem tem `role=admin` ou `is_organizer` (gate em `app/admin/page.tsx` e `app/admin/tournaments/new/page.tsx`).
2. **`tournament_staff`** (por torneio): `role` organizer/arbiter delegado por torneio específico, independente do perfil global.
3. **`board_arbiters`** (por mesa, dentro de um grupo): atribuição de árbitro por número de mesa, **persiste entre rodadas** até troca explícita.

Trigger `trg_prevent_role_escalation` (migration 026) bloqueia usuário comum de alterar o próprio `role` via update direto — só passa se quem está autenticado já for admin, ou se não houver `auth.uid()` (contexto de serviço).

### Identidade do jogador, vagas e check-in (migration 079)

- `user_player_links` é a ponte entre a conta autenticada e o cadastro global em `players`. Aprovar uma inscrição autenticada cria o vínculo verificado; IDs CBX/FIDE idênticos foram retroalimentados com segurança. A Central do Jogador nunca deve inferir identidade apenas pelo nome.
- O limite conta participantes ativos mais inscrições pendentes fora da fila. A alocação e a promoção FIFO da lista de espera são serializadas com lock na linha de `tournaments`; não reproduzir essa conta apenas no cliente.
- Check-in do próprio jogador usa `set_my_checkin`; alteração pela organização usa `set_player_checkin`. Ambos são RPCs com autorização no banco — não fazer update direto de `tournament_players` para presença.

### Inscrição pública sem login

O formulário envia para `POST /api/registrations`. A rota gera o UUID e faz INSERT sem `.select()` com o cliente da sessão (inclusive anônimo), preservando RLS e triggers. Só após sucesso, lê via cliente administrativo os três campos de confirmação (`id`, `payment_status`, `is_waitlisted`) exclusivamente desse UUID gerado no servidor. Não liberar SELECT público de `tournament_registrations`: contém dados pessoais. Encadear `.insert(...).select(...)` no cliente quebra a inscrição anônima, pois apenas a organização pode ler a linha. Regressão: `lib/__tests__/anonymous-registration.test.ts`.

### WO, byes e desempates nativos (FIDE 2026)

Migration `20261028130450_fide_2026_unplayed_standings.sql`: `recalculate_standings` trata os artigos 16.3–16.5 para suíços nativos/app, recalcula também ausentes/desistentes e não sobrescreve importados. Rodada pendente não é ausência; rascunho não pontua. O progressivo inclui todas as rodadas iniciadas até o horizonte de cada grupo. `games_played` e V/E/D contam só partidas no tabuleiro. O critério existente `wins` é **WON**, não **WIN** (vitórias sem jogar); UI explicita isso. Duplo WO preserva o adversário no TRF com cor `-`. A cópia de `progressive` é feita por `sync_player_scores_from_standings`, como os demais campos.

Regressão SQL com rollback: `node --env-file=.env.local scripts/test-fide-standings.mjs`. Exportação/checker dos torneios de auditoria: `node --env-file=.env.local --import tsx scripts/test-audit-trf.mjs`. Ver `docs/qa/correcao-suico-wo-bye-2026-10-28.md` para expectativas, publicação e rollback. Não fazer backfill de torneios históricos/importados em massa: a migration só troca as definições das funções.

## Convenções deste projeto

- **Migrations**: nome `<versão>_<nome>.sql`, sempre idempotentes (`if not exists`, `create or replace`). As `001`–`083` são o histórico antigo, congelado (não criar mais nesse formato). **Novas usam timestamp `AAAAMMDDHHMMSS_nome.sql`** (o mesmo formato do Supabase CLI e do MCP), e a versão tem que ser ÚNICA entre arquivos — duas sessões criando migration no mesmo minuto já colidiram (`…210000_`); confira com `check-migrations`. **Toda migration aplicada precisa estar registrada** em `supabase_migrations.schema_migrations`: o `apply-sql.mjs` registra sozinho, na mesma transação. Se alguém aplicar por fora (painel do Supabase ou MCP `apply_migration`, que gera a própria versão), traga o arquivo para cá com o MESMO nome que o registro tem. As cinco `20260831…`/`20260910…` (`broadcast_*`) são do app de transmissão "Chess Match Film", que divide este banco, e foram recuperadas do registro.
- **Função `security definer` sempre com `set search_path = public, pg_temp`** (ou `alter function ... set search_path`). Sem isso ela roda com o caminho de busca de quem chama e um objeto sombreado em outro schema seria usado com os privilégios do dono (aviso `function_search_path_mutable` do Supabase). As 56 antigas foram corrigidas pela migration `20261023100000`; use `auth.uid()` etc. sempre qualificado.
- **Aplicar migration**: um script só, `scripts/apply-sql.mjs` (os `apply-NNN.mjs` por migration foram removidos em 2026-10-24) — conexão `pg` direta, numa transação, registra a versão no fim: `node --env-file=.env.local scripts/apply-sql.mjs <arquivo.sql> [tabela ...]`. `--register-only <arquivo.sql>` só registra, sem rodar o SQL (para migration já aplicada por outro meio). **`node --env-file=.env.local scripts/check-migrations.mjs`** compara arquivos x registro (versão repetida, arquivo sem registro, registro sem arquivo, nome diferente) e sai com erro se achar algo — rode antes de dar migration como concluída. **A `SUPABASE_DB_URL` está no `.env.local`** (gitignored, nunca commitar): host direto `db.<ref>.supabase.co:5432`, que **resolve do sandbox do agente** (tem rota IPv6 — o `ENETUNREACH` só acontece em rede local sem IPv6). Os scripts leem `process.env.SUPABASE_DB_URL`, não carregam dotenv sozinhos. **`pg` não está nas deps do chess-viewer** — instalar com `npm i pg --no-save` ou usar o de `../cron-import/node_modules`. Alternativas: pooler `postgres.<ref>@aws-1-us-east-2.pooler.supabase.com:6543` (IPv4, mas exige a região certa — deste projeto é `us-east-2`), ou colar o SQL no **SQL Editor** do dashboard (e depois `--register-only`). Verificações **read-only** também dá via REST (`curl` com `service_role` key, HTTPS, não depende de IPv6). **Senha do banco vive só no `.env.local`, nunca em arquivo tracked (CLAUDE.md incluso) — vai pro histórico do git e pro GitHub.**
- **Mock da Asaas nunca vale em produção** (`VERCEL_ENV=production`): sem `ASAAS_API_KEY` lá, cobrar dá erro em vez de gerar pagamento falso, e `/api/mock/asaas-confirm` responde 404 (`asaasMockAllowed()` em `lib/asaas/client.ts`). Em dev/preview sem chave o mock continua funcionando.
- **Env var cujo valor começa com `$` (caso real: `ASAAS_API_KEY`) tem comportamento DIFERENTE nos dois loaders de env do projeto** — o `@next/env` (que o `next dev`/build usa) faz expansão tipo shell, então `ASAAS_API_KEY=$aact_...` carrega **vazia** (e o cliente Asaas caía em modo mock em silêncio, sem erro nenhum); `\$aact_...` resolve pro Next, mas `node --env-file=.env.local` (todo `apply-NNN.mjs` e script de teste) **não** processa o escape e entrega a barra literal, o que vira 401 na Asaas. Testado: nenhuma forma de quoting (`"..."`, `'...'`) serve pros dois. Convenção adotada: escapa no `.env.local` (`\$`) e normaliza no consumidor (`lib/asaas/client.ts` faz `key.replace(/^\\/, '')`). Na Vercel o valor é cru, sem barra — lá não existe expansão. Ao adicionar env nova com `$`, `` ` `` ou `\` no valor, conferir o valor efetivo **nos dois caminhos** antes de dar como configurado.
- **Tipos do banco**: `types/database.generated.ts` é GERADO — não editar à mão. Depois de toda migration que mude tabela, coluna, enum ou função em `public`, rode `node --env-file=.env.local scripts/gen-types.mjs` (`npm run gen-types`; usa o mesmo gerador do `supabase gen types`, sem Docker, só `pg` + `@supabase/typegen`, ex.: `TYPEGEN_FROM=../pgtool`) e commite o arquivo junto com a migration. `types/database.ts` só guarda os tipos de domínio (`Tournament`, `StandingRow`…) e reexporta `Database`. Colunas `text` com check (status etc.) chegam como `string`: faça cast para o tipo de domínio na borda (ver `lib/reports/orders.ts`). **`npm run type-check` está em 0 erros e roda no CI antes do deploy** — o `next build` continua ignorando tipos (`ignoreBuildErrors`), então o CI é a barreira; não introduza `as any` para escapar de erro de tipo do cliente Supabase, as tabelas estão todas tipadas. Do `next-intl`: o `redirect` de `@/i18n/navigation` exige `{ href, locale }`; para ir ao login use `redirectToLogin()` de `lib/data/session.ts` (redirect com string vira `/undefinedundefined`).
- **Lint**: `npx next lint` deve dar zero *Error* (warnings de `no-explicit-any` são pré-existentes e tolerados). A pendência antiga dos ~520 erros de tipo (`docs/pendencia-tipos-supabase.md`) foi resolvida: ver "Tipos do banco" acima.
- **`npm run build` local falha com `EISDIR`** em máquina Windows — confirmado que é ambiente local, não o código (a main limpa falha igual). A Vercel builda em Linux normalmente; esse é o gate real, não o build local.
- **Testes**: `npx vitest run lib/pairing` — golden tests contra fixtures reais do bbpPairings upstream (`lib/pairing/__tests__/fixtures/`, licença Apache 2.0 preservada).
- **Deploy**: push em `main` dispara GitHub Actions → Vercel (produção direta, sem branch de preview neste fluxo). Sempre conferir o resultado do run (`gh run list` / `gh run watch`) antes de dar como concluído.
- **Teste no browser interno do agente (preview pane)**: páginas **server component** (`/`, `/admin`, `/torneios/...`) renderizam normal, mas páginas **client-gated por auth** (as abas de `/admin/tournaments/[slug]/...`, `/admin/tournaments/new` — que dependem de `useUser`/`useProfile`) ficam presas em "Carregando…" nesse browser sandbox: o `getUser()` client por cookie não resolve (particionamento de cookie/storage). Não é bug do app. Pra validar essas telas, usar Chrome real; no preview pane dá pra validar só o que é server-rendered. Cadastro de teste: `/` → "Cadastre-se" marca "Organizar torneios" → nasce com `is_organizer=true` sem precisar mexer no banco.
  - **A causa é mais ampla que cookie**: o browser do sandbox **não alcança o host do Supabase** (o console mostra `503 (Offline)` nas chamadas). Então **qualquer** página que busque dado pelo cliente fica em "Carregando…" ali — inclusive página pública sem auth nenhuma, como `/torneios/[slug]/standings`. O **servidor** do dev tem rede normal (mesma rota que faz o `apply-NNN.mjs` funcionar). Receita prática: `preview_start`, e validar Server Components por `curl` + grep no HTML (ex.: `curl -s .../standings/print | grep -o '<h3>[^<]*</h3>'`) em vez de tentar ler a tela no browser. Pra exercitar as duas pontas de um flag, alternar a coluna direto no banco entre dois `curl` — e **restaurar o valor depois**.

## Erros de UX já cometidos e corrigidos (não repetir o padrão)

- **Spinner infinito por comparação com `null`**: `statusSaving === prevStatus` quando ambos podem ser `null` em estados diferentes (idle vs "não há estágio anterior") dá falso positivo. Sempre checar truthy explícito antes de comparar dois valores potencialmente nulos com significados distintos.
- **Cabeçalhos duplicados/inconsistentes por página**: antes de adicionar um link de navegação num header de página admin, checar se `components/admin/admin-tournament-tabs.tsx` (o layout compartilhado em `app/admin/tournaments/[slug]/layout.tsx`) já cobre isso — não duplicar.
- **Card de import do chess-results sem guarda de modo**: qualquer feature exclusiva de um modo (`native`/`imported`) precisa checar `tournament.mode` explicitamente na UI, não só confiar na RLS/trigger do banco (que bloqueia mas não esconde, gerando erro feio em vez de a opção simplesmente não aparecer).
- **Registro manual de jogador sem grupo**: ao adicionar `tournament_players` em torneio nativo, `pairing_group_id` é obrigatório (trigger recusa). Toda tela que insere participante precisa oferecer o seletor de grupo, não só o RPC de pareamento.
- **`approve_registration` reaproveitando `players` por nome sem atualizar dado novo** (migration 046): o find-or-create casa por CBX/FIDE/nome; ao achar um `players` já existente, só `sex` era retroalimentado (se nulo) — `birth_year`/`city`/`federation`/`fide_id`/`cbx_id`/`rating_std` da inscrição nova eram descartados em silêncio. Sintoma: segunda inscrição pro mesmo nome com idade preenchida aprovava sem classificação (derive_player_category depende de `birth_year`). Qualquer UPDATE de "enriquecer cadastro existente com dado novo" precisa cobrir todos os campos que a inscrição pode trazer, não só o que motivou o bug original.
- **Campo "puramente informativo" que devia ter virado regra e não virou** (migration 044 → 047): `tournaments.start_time` nasceu só pra exibição, mas a regra automática de status (`next_status_by_date`) continuou comparando só `start_date`, então um torneio com horário à noite virava `ongoing` de manhã. Ao adicionar um campo de horário/data granular numa tabela que já tem uma regra de transição por data, checar se essa regra não devia (ou já devia) considerar o campo novo — "informativo" às vezes é só o estado inicial antes de alguém pedir que passe a valer.
- **Reaproveitar componente feito pra redirect dentro de um embed inline**: `ClassificationSetup` (aba Editar) tinha `window.scrollTo(0, 0)` forçado ao carregar — fazia sentido lá (destino de um redirect, página curta antes do conteúdo chegar). Ao embutir o mesmo componente no meio da tela de criação (opção "Personalizado", sem navegar), esse scroll forçado virava exatamente o "pula a página" que o usuário reclamou. Precisou de prop (`autoScrollTop`, default `true`) pra desligar só no caso embutido. Mesmo componente também renderizava a seção "Classificação" de novo, duplicada, empurrando o "Emparceiramento" pra baixo — a tela de criação já mostra essa parte no rascunho acima; precisou de outra prop (`showClassification`, default `true`) pra esconder só no embed. Regra geral: componente feito pra uso standalone (efeito colateral de página inteira, ou seções que fazem sentido sozinhas) pode duplicar conteúdo ou quebrar quando embutido no meio de outra tela — sempre checar isso, e preferir prop opcional (default = comportamento antigo) a duplicar o componente.
- **Botão de resultado que some ao invés de destacar** (painel do árbitro, `rounds/[roundId]/results/page.tsx`): lançar resultado trocava os botões por texto — corrigir exigia achar um link "corrigir" escondido. Pedido do usuário: pra uma ação que pode ser revertida/alterada até um estado fechar (rodada encerrar), o controle que a disparou devia continuar visível e clicável, só destacando a opção atual — não sumir e virar outra coisa.
- **Emparceiramento saiu da tela de criação e virou aba própria** (`app/admin/tournaments/[slug]/groups`, antes um redirect morto pra `/edit`): decidir "por idade/rating/personalizado" na hora de criar exigia embutir `ClassificationSetup` inline (ver bullet acima) só pra liberar o mapeamento "Personalizado". Trocado por: criação decide só Classificação (emparceiramento sempre nasce `absolute`, grupo "Absoluto"); emparceiramento de verdade (incluindo trocar pra `custom`) mora numa aba separada, disponível a qualquer momento depois. Corolário: `pairing_mode='custom'` sem grupo criado ou com classificação sem grupo mapeado deixa o torneio num estado que `enforce_native_pairing_group` rejeitaria no primeiro jogador aprovado — por isso "Publicar" (`admin-tournament-chrome.tsx`) trava nesse caso, calculado em `layout.tsx` (`pairingReady`).
- **Flash "Entrar" → "Minha conta" no header** (e bolha do Gambito "pipocando"): `Header`/`ChatWidget` derivavam auth só no client (`useUser`, round-trip `getUser` pós-hidratação), montados no layout raiz. Corrigido passando `initialUser` do servidor: `app/layout.tsx` virou `async`, lê `getUser()` e injeta nos dois; enquanto `useUser().loading`, usa o `initialUser` (primeiro paint correto), depois passa pro live (reage a login/logout). Não voltar a montar componente auth-dependente no layout raiz sem esse fallback de servidor.
- **Home `/` sequestrava todo mundo pro último torneio**: `middleware.ts` redirecionava qualquer acesso a `/` pro cookie `last_tournament` (só o logo tinha bypass `?home=1`) — PWA, URL digitada e 404 ficavam presos no torneio. Agora só redireciona **anônimo**; logado tem home própria. `?home=1` expira o cookie (start_url da PWA usa `?home=1`). Não reintroduzir redirect de `/` pra logado. **Revisado depois** (ver bullet "Home do organizador deixou de SUBSTITUIR a landing" abaixo): `/` não roteia mais entre duas telas — todos recebem `marketing-home.tsx`, e o organizador ganha `organizer-dashboard.tsx` embutido no lugar do hero.
- **Ritmo de jogo virou select + coluna `time_control_kind`** (migration 061): `time_control` continua sendo o texto exibido; `time_control_kind` (enum bullet/blitz/rapid/classical/other) é a categoria pra busca/estatística. Presets em `lib/utils/time-control.ts` (fonte única); escolher um preset sugere o `rating_kind` de seed **sem forçar** (só até o organizador mexer manualmente). "Outro" revela o campo de texto livre.
- **Busca de staff por nome/e-mail** (migration 062, `search_staff_candidates`): `user_profiles` tem RLS self-read, então `.ilike()` do client volta vazio — autocomplete precisa de RPC `security definer` gated por `is_tournament_organizer`. Padrão reusável pra qualquer busca em `user_profiles` a partir do client. O RPC de escrita continua `add_staff_by_email` (a busca só preenche o e-mail que ele já consome).
- **Selo cosmético que ignorou o override que o backend já respeitava** (migration 045 → 063): "Reabrir Inscrições" põe `registration_closes_by_date=false` e o status real fica `registration` (aberto), mas `isRegistrationClosed` (`lib/utils/chess.ts`) decidia o rótulo/cor do badge só por `registration_end_date < hoje` — mostrava "Inscrições encerradas" mesmo com o torneio aberto. O estado durava (fix de 045 no banco), o *selo* é que não recebeu o interruptor. Corrigido passando `registration_closes_by_date` até `isRegistrationClosed`/`getTournamentStatusLabel`/`getTournamentStatusColor` (3º param, default `true` = default do banco) em TODOS os call sites (admin/page, organizer-dashboard, players, tournament-card, chrome, layouts público e admin). `search_tournaments` (RPC da lista pública) não projetava o campo — migration 063 só o adiciona à projeção; `TournamentListItem` ganhou o campo. Regra: ao criar uma regra de negócio com "interruptor" (flag que muda o comportamento por data), varrer TODA derivação cosmética daquele estado (labels, cores, ícones) — não só a transição real; senão a UI mente sobre um estado que o backend já corrigiu.
- **Rodada 1 NÃO é mais gerada sozinha (2026-10-29, pedido do dono)**: nem no clique em "Iniciar Torneio" nem ao abrir a aba Rodadas — o organizador precisa marcar ausências (bye pedido) ANTES de parear, e a rodada já pareada nascia sem considerar quem falta. Iniciar o torneio só gera o ranking inicial (seed); a rodada 1 sai do botão "Gerar rodada 1". O bullet abaixo descreve o desenho antigo (duas camadas) e fica só como registro do porquê a engine WASM não roda no banco; se a geração automática voltar, ela tem que esperar o organizador poder marcar ausências.
- **Automação que depende da engine tem que viver em DUAS camadas, não numa trigger**: a rodada 1 automática nasceu só no clique em "Iniciar Torneio" (`admin-tournament-chrome.tsx`), e por isso não acontecia pro torneio que vira `ongoing` sozinho por data (`next_status_by_date`, 040/047). A tentação é pôr no banco junto com o auto-seed da 058 — **não dá**: bbpPairings é WASM e só roda em API route Node. A segunda camada é lazy na leitura (`native-rounds.tsx`: gera na primeira abertura da aba Rodadas com torneio em andamento e grupo sem rodada), mesmo padrão do status corrigido na leitura. Funciona porque rascunho não tem consumidor externo — o público só vê rodada publicada, então gerar quando o organizador abre a tela equivale a gerar no instante da virada. Guardas obrigatórias nesse tipo de efeito: `useRef` pra falha não virar loop de retry, e não disparar com grupo vazio (`NO_PLAYERS` viraria erro na tela a cada abertura).
- **`publish_round` NÃO muda o status do torneio** (migration 020): só a rodada vai pra `ongoing`. O torneio vira `ongoing` pela regra de data ou pelo stepper. Consequência: "rodada 1 publicada" e "torneio em andamento" são fronteiras independentes — dá pra ter uma sem a outra nos dois sentidos. O aviso "Podem ser editadas até a 1ª rodada ser publicada" no card Gerenciamento (`tournament-form.tsx`) descreve essa fronteira, mas o congelamento implementado é por status (`ongoing`/`finished`, em `edit/page.tsx`); se algum dia a regra tiver que ser "na publicação da rodada 1", o critério muda e o texto passa a valer.
- **Home do organizador deixou de SUBSTITUIR a landing e virou bloco dentro dela** (revisão do bullet "Home `/` sequestrava todo mundo"): `organizer-home.tsx` trocava a página toda pela lista de torneios do organizador — e com isso ele perdia "Acontecendo agora", notícias e recursos, que também quer ver. Virou `organizer-dashboard.tsx`, passado como slot `dashboard` pro `MarketingHome`, que o renderiza **no lugar do hero** (o hero é discurso de venda: inútil pra quem já usa o produto, e caro porque ocupa a primeira tela inteira). Duas lições reusáveis: (1) "trocar a tela por outra" costuma ser pior que "compor as duas" quando os dois conteúdos interessam ao mesmo usuário — preferir slot a bifurcação de rota; (2) componente que era página inteira e passa a ser embutido precisa perder o que a página hospedeira já mostra (aqui, a chamada "Ver torneios públicos", que duplicava as seções logo abaixo) — mesmo padrão já registrado pro `ClassificationSetup`.
- **"Absoluto" agora significa DUAS coisas — sempre desambiguar** (migration 065): a **classificação** absoluta (`tournaments.has_absolute_classification`, o ranking transversal a todas as faixas, aba da classificação pública) e o **grupo de emparceiramento** chamado "Absoluto" (que todo torneio nativo recebe na criação, `create-tournament-setup.ts`). Uma é premiação, a outra é quem joga contra quem. Escolha consciente do usuário ao renomear a aba "Geral" → "Absoluto"; a KB do Gambito (`docs/kb/classificacao-e-emparceiramento.md`) tem um aviso explícito separando os dois — não remover.
- **Eixo transversal não é linha da partição.** As classificações são uma partição (`derive_player_category`, 035, escolhe a mais específica que casa), então a tentação de modelar o absoluto como um `tournament_categories` com critérios nulos está errada: ele casaria com qualquer um e viraria o balde de sobra — que é exatamente o que a célula vazia descartada em `generateClassificationCells` já era. Absoluto é atributo do torneio (coluna), não categoria. Vale pra qualquer recorte "todo mundo aparece nele" que apareça depois. Corolário de UI: desligar o eixo transversal precisa de guarda em runtime (`showAbsolute` em `standings/page.tsx` e no `/print`) porque o organizador pode desligar a chave e depois apagar todas as faixas — sem a guarda a classificação apareceria vazia.
- **Form inteiro somente-leitura: `<fieldset disabled>`, não `disabled` campo por campo.** Desabilita nativamente todo input/select/textarea/button descendente — cobre chips e pickers que não são inputs registrados no react-hook-form (Cobrança, `TiebreakOrderPicker`) e cobre de graça campo novo adicionado depois. Duas pegadinhas: precisa de `min-w-0` (o `min-width: min-content` padrão do fieldset estoura grid de 2 colunas em tela estreita), e botão de submit que vive FORA do form via atributo HTML5 `form=` também fica fora do fieldset — tem que ser escondido/desabilitado à parte.
- **Layout compartilhado (`app/torneios/[slug]/layout.tsx`) reroda TODA sua busca de dado em CADA navegação entre abas** (rota dinâmica por causa do client Supabase por cookie, sem cache entre requests) — chegava a 4 queries sequenciais em Node só pra montar cabeçalho/abas (status corrigido por data, rodada atual, status efetivo, último sync), sem Suspense em volta de si mesmo, então a tela ficava travada sem feedback até a cadeia inteira resolver. Corrigido (migration 071, `get_tournament_page_data`): calcula tudo isso dentro do Postgres, 1 round-trip só. Página filha (`participants/page.tsx`) também rebuscava o torneio que o layout já tinha — corrigido com `lib/data/tournament-page-data.ts` (função envolvida em `cache()` do React: layout e página filha que pedem o mesmo slug dividem a mesma chamada dentro do request). Padrão geral: **qualquer layout ou página que faça `await supabase...` sequencial** (uma espera a outra sem depender do resultado) devia usar `Promise.all`; e **qualquer dado que o layout já buscou não devia ser rebuscado pela página filha** — usar `cache()` em vez de duplicar a query. Ao adicionar nova aba/rota sob um layout dinâmico, checar se o layout não está pagando essa conta de novo a cada clique.
- **SSR em `next dev` neste Windows não serve de medida de performance real** (mesma família do bug já documentado de `npm run build` EISDIR): uma tabela com 275 linhas levou ~10-12s pra renderizar em dev mesmo com o fetch de dado já em ~1s — isolado via `console.time` e confirmado com A/B (`git stash`) que o código antigo tinha o mesmo tempo, ou seja, não é regressão de mudança nenhuma, é o ambiente. Log mostra `Caching failed for pack: Unable to snapshot resolve dependencies` repetido, mesma race de filesystem/webpack cache. Não confiar em tempo de resposta medido em dev local pra validar fix de performance — só serve pra confirmar que a QUERY em si ficou mais rápida (via timer isolado ao redor só do fetch); pra latência de ponta a ponta, medir em produção depois do deploy.

- **Select de coluna nova publicado antes da migration derruba a página INTEIRA, não só o campo** (2026-10-16, `players.fide_name`): a lista de participantes e a página do jogador passaram a pedir `fide_name` dentro de `players(...)`; o código foi pro ar antes de a coluna existir e o PostgREST recusou a consulta toda — "Nenhum participante neste grupo" em TODOS os torneios por ~15 min, sem erro visível. Valor opcional em TypeScript (`?.`) não protege: o erro é da query, não do campo. Ordem obrigatória quando o código lê coluna nova: **aplicar a migration primeiro, depois publicar o código**. Só o que lê por RPC antiga (que ainda não devolve a coluna) é seguro publicar antes.
- **Recriar função (`drop` + `create`) a partir de uma definição VELHA apaga colunas acrescentadas depois** (2026-10-16): a migration `20261016120000` copiou `get_player_tournament_history` da 077, mas a 20261005190000 já tinha acrescentado `opponent_tp_id` — o adversário deixou de ser link na página do jogador, sem erro nenhum (corrigido em `20261016170000`). Antes de recriar uma função, `grep -l "nome_da_funcao" supabase/migrations/*.sql` e partir da ÚLTIMA definição (nome do arquivo mais recente), não da que aparece primeiro.

- **Desempate calculado no mesmo loop que grava os pontos lê pontuação velha** (2026-10-21, migration `20261021160000`): `recalculate_standings` gravava `current_score` de um jogador e, na mesma volta, somava Buchholz/BH-1/SB com o `current_score` dos adversários — quem o loop ainda não tinha visitado vinha com o valor do recálculo anterior, então os desempates ficavam um resultado atrasados (numa carga do zero, zeros). Passou despercebido porque encerrar a rodada recalcula de novo e "conserta". Regra: qualquer cálculo que dependa de um valor derivado de OUTRAS linhas (Buchholz depende dos pontos dos adversários) precisa de duas etapas — primeiro grava o valor base de todos, depois calcula o derivado.

## Fluxo de trabalho — gated por pedido explícito (não antecipar etapa)

Pedido de **alteração** ("muda X", "corrige Y") → só:
1. Editar código (achar causa raiz antes, não só sintoma/UI).
2. Se houver migration nova: criar `supabase/migrations/AAAAMMDDHHMMSS_nome.sql` idempotente — mas **não rodar** a menos que peçam pra testar/publicar.

Pedido de **testar** ("testa isso", "confere se funciona") → adiciona:
3. `npx next lint` (esperar 0 *Error*) + `npx vitest run lib/pairing` quando mexeu em pareamento.
4. Rodar migration nova (`scripts/apply-sql.mjs`, que registra a versão) se ainda não rodou.
5. Verificar visual/comportamento (preview local no browser) quando a mudança for observável ali.

Pedido de **publicar/push** ("publica", "sobe", "faz push") → adiciona:
6. Commit em português, mensagem explicando o *porquê*, não só o *o quê*.
7. `git push origin main`.
8. Monitorar o deploy (`gh run watch` em background) antes de reportar concluído.
9. Registrar no `CLAUDE.md` (seção "Erros de UX já cometidos" ou equivalente) se foi bug/padrão que vale não repetir.

**Não pular etapas de um pedido pro outro** — "muda X" não implica testar nem publicar; "testa" não implica publicar. Só avança de fase quando o usuário pedir explicitamente.

## Chatbot de suporte (Gambito) — RAG + tool calling + escalonamento

Plano original em `docs/plano-chatbot-suporte.md`; desvios e status real em `docs/pendencias-chatbot.md` (leia antes de mexer, tem histórico de todas as migrations 048-055).

- **Arquitetura**: pergunta → embedding (Voyage AI `voyage-4-lite`) → `match_kb_chunks` (pgvector, `kb_chunks`) → contexto no prompt (`lib/chat/prompt.ts`) → LLM gera resposta, com **tool calling** disponível pra 3 ferramentas (`lib/chat/tools.ts`, formato neutro/JSON Schema puro): contar torneios por estado, contar meus torneios, registrar pergunta sem resposta. `lib/chat/llm.ts` implementa o loop pros dois provedores (`generateWithAnthropic`/`generateWithGemini`), cada um adaptando `TOOL_DEFINITIONS` pro formato de tool use específico (Anthropic: `input_schema` quase 1:1; Gemini: `Type` enum via `toGeminiDeclarations()`).
- **Provedor ativo (2026-08-03): Anthropic** (`CHAT_LLM_PROVIDER=anthropic`, `claude-haiku-4-5-20251001`) — decisão do usuário de abandonar o Gemini. Motivo: free tier do Gemini (`gemini-3-flash-preview`) é **só 20 requisições/dia por modelo** (bem mais restrito do que a doc geral do Gemini sugere) — estourava fácil só testando. Código do Gemini continua no repo (arquitetura trocável), sem previsão de uso.
- **Comportamento de tool-calling difere entre modelos**: testado que Claude Haiku só chama `registrar_pergunta_sem_resposta` pra pergunta plausivelmente dentro do domínio mas fora da KB (ex.: "como transferir organização de torneio") — pergunta claramente fora de assunto (ex.: "horário de lotérica") ele responde direto sem chamar a ferramenta, porque já sabe redirecionar sem precisar registrar. Gemini era mais "gatilho fácil", chamando a ferramenta também pro caso óbvio. Ambos os comportamentos são aceitáveis — o de Claude até evita poluir `unanswered_questions` com pergunta claramente fora de escopo.
- **Gemini com thinking exige ecoar `thoughtSignature` de volta** na chamada seguinte de um loop de tool-calling, senão a API rejeita com "Function call is missing a thought_signature". Por isso `generateWithGemini` usa `response.candidates[0].content.parts` (o Part cru) em vez do getter de conveniência `response.functionCalls` (que descarta esse campo).
- **Escalonamento pra humano (Fase 3, migration 051)**: sem Realtime (maior risco técnico do projeto, nunca usado aqui) — widget e painel usam polling (`refetchInterval`). Resposta do admin grava como `role='assistant'` (nunca `'operator'`) — decisão do usuário: a ilusão "é sempre o Gambito" nunca quebra pro usuário final; `chat_messages.is_human` guarda a distinção só pra revisão interna.
- **App Android do admin** (`workspace-gambito-admin`, projeto irmão fora deste repo): fala direto com o Supabase via `supabase-kt`, autenticado como a própria conta admin — sem API própria. Liberado por policies de escrita direta (`chat_messages_insert_admin`/`chat_sessions_update_admin`, migration 052) que o painel web não precisa (usa `service_role` via `/api/chat/reply`).
- **Log de erros** (`error_logs`, migration 053) e **perguntas sem resposta** (`unanswered_questions`, migration 055): duas tabelas de observação, só admin lê (`/admin/dev/errors`, `/admin/dev/unanswered`, e as mesmas telas no app Android). Escrita sempre via `service_role` (`lib/log-error.ts`) ou pela ferramenta de tool-calling — nenhuma das duas tem policy de insert pro client comum.

### Testando o chat em e2e (Playwright) — pegadinha de sessionId

`ChatWidget` lê `xbr_chat_session_id` do localStorage **uma única vez**, no `useEffect` de mount (dependências vazias) — e como ele mora no layout raiz, não desmonta na navegação client-side entre `/login` e `/admin`. Setar o valor via `page.evaluate()` **depois** de `page.goto('/login')` não funciona: o widget já montou e já leu (valor antigo/nulo) antes do `evaluate` rodar. Precisa de `context.addInitScript(...)` (roda antes do JS da página, em toda navegação) — e mesmo assim, se a sessão de chat já existir via localStorage na primeiríssima carga pós-login, a query de mensagens pode disparar antes do cliente Supabase do browser terminar de hidratar a sessão de auth (corrida que o fluxo normal nunca expõe, porque `sessionId` só aparece depois do primeiro round-trip de mensagem, vários segundos depois). Um `page.reload()` + `waitForLoadState('networkidle')` logo após o login resolve. Ver `e2e/chat-escalation.spec.ts`.
